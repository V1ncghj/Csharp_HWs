# ДЗ 9. Часть 1 — Задачи на понимание

## Задача 1. Анализ JSON-сериализации

Дан класс:

```csharp
public class Player
{
    public string Name { get; set; }
    public int Score { get; set; }
    private int secretCode = 42;
    public bool IsAlive;
}
```

Код:

```csharp
Player p = new Player() { Name = "Alex", Score = 100, IsAlive = true };
string json = JsonSerializer.Serialize(p);
```

### а) Что попадёт в JSON?

Результат сериализации:

```json
{"Name":"Alex","Score":100}
```

По правилам `System.Text.Json`:

| Член класса | Попадёт в JSON? | Почему |
|---|---|---|
| `Name` | ✅ Да | Публичное свойство с публичным геттером — сериализуется всегда |
| `Score` | ✅ Да | Публичное свойство с публичным геттером — сериализуется всегда |
| `secretCode` | ❌ Нет | Это **private**-поле. Сериализатор работает только с публичными членами |
| `IsAlive` | ❌ Нет | Это публичное **поле**, а не свойство. По умолчанию `System.Text.Json` сериализует только свойства (properties), поля (fields) игнорируются |

### б) Как включить secretCode в JSON, оставив его приватным?

Нужно заменить поле на свойство, у которого геттер публичный, а сеттер приватный:

```csharp
public int SecretCode { get; private set; } = 42;
```

Сериализация использует **геттер**, и поскольку он публичный, значение попадёт в JSON. Сеттер остаётся недоступен снаружи — инкапсуляция сохраняется (снаружи значение по-прежнему нельзя изменить, только прочитать).

Если сделать приватным ещё и геттер (`private int SecretCode { get; set; }`), понадобится атрибут `[JsonInclude]` — он разрешает сериализатору использовать непубличные акцессоры.

### в) Почему IsAlive не попадает в JSON и два способа исправить

`IsAlive` объявлено как **поле** (`public bool IsAlive;`), а `JsonSerializer` по умолчанию сериализует только **свойства**.

**Способ 1 — превратить поле в свойство:**

```csharp
public bool IsAlive { get; set; }
```

**Способ 2 — разрешить сериализацию полей через атрибут `[JsonInclude]`:**

```csharp
[JsonInclude]
public bool IsAlive;
```

(альтернатива — глобальная настройка `new JsonSerializerOptions { IncludeFields = true }`, тогда сериализоваться будут все публичные поля всех классов).

## Задача 2. Восстановление объекта из JSON

### а) Класс для десериализации

```csharp
public class Game
{
    public string Title { get; set; }        // "Dark Souls" — строка
    public int Year { get; set; }            // 2011 — целое число
    public double Rating { get; set; }       // 9.5 — дробное число
    public string[] Genres { get; set; }     // ["RPG","Action"] — массив строк
    public bool IsMultiplayer { get; set; }  // true — логическое значение
}
```

Десериализация:

```csharp
Game game = JsonSerializer.Deserialize<Game>(json);
```

Типы подобраны по значениям: год без дробной части → `int`, рейтинг с дробной частью → `double`, массив строк → `string[]`, `true/false` → `bool`.

### б) Ключ `Title` заменили на `title` — почему сломалось и как починить

`System.Text.Json` по умолчанию сопоставляет ключи JSON со свойствами **точно по имени и с учётом регистра**: `"title"` не равно `Title`, поэтому сопоставление не происходит и свойство остаётся со значением по умолчанию (`null`).

Решение — включить нечувствительность к регистру в настройках, не меняя имена свойств:

```csharp
var options = new JsonSerializerOptions
{
    PropertyNameCaseInsensitive = true
};
Game game = JsonSerializer.Deserialize<Game>(json, options);
```

Теперь `"title"` корректно сопоставится со свойством `Title`.

### в) Валидна ли строка `[1,"hello",true,null]`?

**Да, это валидный JSON** — массив из четырёх элементов разных типов (число, строка, булево значение, null). Ограничение «один тип на массив» у JSON отсутствует.

В C# такой массив не десериализуется в строго типизированный массив вроде `int[]` или `string[]` (типы элементов разные). Подходящие варианты:

```csharp
// 1. JsonElement — универсальное представление любого JSON
JsonElement array = JsonSerializer.Deserialize<JsonElement>(json);

// 2. Массив object? / List<object?> — каждый элемент в своём типе
object[] items = JsonSerializer.Deserialize<object[]>(json);
```

Чаще всего для «неизвестной» структуры JSON используют `JsonElement` (или `JsonNode`).

## Задача 3. File vs FileStream — выбор инструмента

| № | Сценарий | Инструмент | Обоснование |
|---|---|---|---|
| 1 | Прочитать маленький конфиг (10 строк) целиком | **File** (`File.ReadAllText`) | Файл маленький, нужно одно простое чтение целиком — не нужно вручную управлять потоком |
| 2 | Автосохранение прогресса игры в файл | **File** (`File.WriteAllText`) | Каждый раз сохраняется целостное состояние целиком, перезаписывая файл — одна строчка кода, поток открывается и закрывается автоматически |
| 3 | Логирование: дописывать строки в лог-файл до нескольких ГБ | **FileStream** (`FileMode.Append`) | Файл огромный — открываем поток один раз в режиме дозаписи и держим его открытым; ничего лишнего не читается и не перезаписывается |
| 4 | Проверить существование файла сохранения и прочитать целиком в строку | **File** (`File.Exists` + `File.ReadAllText`) | Проверка существования и чтение целиком — обе операции являются «фасадными» методами именно класса `File` |
| 5 | Заменить 10 байт в середине большого бинарного файла, не перезаписывая его | **FileStream** (`FileMode.Open`, `Seek` + `Write`) | Нужен произвольный доступ: открываем существующий файл, перемещаемся по позиции (`Seek`) и перезаписываем только нужные 10 байт. `File` так не умеет — его методы работают с файлом целиком |

**Общее правило:** `File` — удобная обёртка для операций «всё сразу» (прочитать/записать файл целиком, проверить существование, удалить). `FileStream` — когда нужен контроль над процессом: дозапись, чтение/запись по позиции, работа с большими файлами по частям.
