# Часть 1. Задачи на понимание

## Задача 1. Вопросы по коду

### 1. Почему ProcessDamage принимает List<IDamageable>, а не List<Player> или List<Trap>? Что это даёт с точки зрения полиморфизма?

`List<IDamageable>` позволяет одному методу работать с любым объектом, реализующим интерфейс: и с игроками, и с ловушками, и с любыми будущими классами. Это и есть полиморфизм: `GameSystem` не знает и не должен знать конкретные типов целей — он оперирует абстракцией. Если бы метод принимал `List<Player>`, пришлось бы писать отдельные перегрузки для каждого типа, а при добавлении нового класса изменять `GameSystem`. С интерфейсом система открыта для расширения: новый класс просто реализует `IDamageable`, и его сразу можно передавать в `ProcessDamage`, ничего не меняя.

### 2. Trap возвращает false и не меняет HP. Нарушение контракта интерфейса? Нормально ли это для вызывающего кода?

Формально контракт не нарушен: метод принимает `int` и возвращает `bool`, код компилируется и выполняется. Однако нарушается семантическое ожидание: метод называется `TakeDamage`, и вызывающий код ожидает, что урон уменьшит HP объекта, а возвращаемое значение отражает, выжил ли он. У ловушки HP задано константой 10, оно не меняется, а метод всегда возвращает false — то есть «объект погиб», хотя его состояние вообще не изменилось. Со стороны вызывающего кода это странно: обработка урона показывает «Ловушка разбилась!» при каждом вызове, даже повторном, и статус объекта не соответствует его реальному состоянию.

### 3. Что было бы, если бы в GameSystem не было ProcessHeal, а зелье пытались бы лечить через ProcessDamage?

`HealthPotion` не реализует `IDamageable`, поэтому передать его в `ProcessDamage` напрямую нельзя — при попытке добавить зелье в `List<IDamageable>` возникнет ошибка компиляции (неявное приведение невозможно). Если бы зелье принудительно привели через каст `(IDamageable)potion`, программа бы скомпилировалась, но при выполнении возникло бы исключение `InvalidCastException`. Кроме того, это концептуальная ошибка: лечить через систему урона — значит смешивать противоположные по смыслу операции, система перестаёт отражать логику игры.

### 4. Если к IDamageable добавить свойство bool IsDead { get; } — какие классы придётся изменить? Что будет, если не сделать?

Придётся изменить все классы, реализующие интерфейс, — в примере это `Player` и `Trap`: в каждый нужно добавить реализацию свойства `IsDead`. Если этого не сделать, код не скомпилируется — компилятор выдаст ошибку, что класс не реализует член интерфейса. Это иллюстрация нарушения принципа разделения интерфейсов (Interface Segregation Principle): раздутый интерфейс обязывает всех его implementors меняться при любом добавлении члена, даже если части классам это свойство не нужно (ловушке-то статус «мертв/жив» по смыслу не подходит — она просто разбивается).

## Задача 2. Таблица «Абстрактный класс vs Интерфейс»

(В файле задания видны только три строки таблицы — заполнены они.)

| Утверждение | Abstract class | Interface |
|---|---|---|
| Может содержать поля с конкретными значениями | + | − |
| Может иметь полноценный конструктор | + | − |
| Может содержать приватные методы | + | + (с C# 8) |

**Комментарии:**

1. **Поля с конкретными значениями.** Абстрактный класс — это обычный класс: он может хранить состояние в полях экземпляра. Интерфейс не может содержать поля экземпляра — только свойства, методы и константы `static`.
2. **Полноценный конструктор.** Абстрактный класс имеет конструкторы, которые вызываются через `base(...)` в наследниках. В интерфейсе конструкторы не объявляются — создавать экземпляр интерфейса нельзя в принципе.
3. **Приватные методы.** В абстрактном классе приватные методы — стандартная практика для вспомогательной логики. В интерфейсе с версии C# 8 также разрешены private-методы, но только с телом (обычно как вспомогательные для default-реализаций); раньше (до C# 8) их было нельзя.

## Задача 3 (дополнительный вопрос). Проектирование системы типов

**Схема (текстом):**

```
              IDamageable                IHealable        IDialogable
             (получает урон)            (лечится)      (открывает диалог)
                   │                         │                 │
                   │                         │                 │
        ┌──────────┴───────────┐             │        ┌────────┴───────┐
        │                      │             │        │                │
   Character (abstract)        │             │        │                │
   Name, HP, TakeDamage() ──────┘             │        │                │
        │                                     │        │                │
   ┌────┼─────┐                               │        │                │
   │         │  │                             │        │                │
 Player    Enemy NPC ─────────────────────────┴────────┴────────────────┘
(ещё
IHealable,
IDialogable)
```

**Объяснение.** Общее состояние и поведение всех трёх сущностей — имя, HP, получение урона — выносим в абстрактный класс `Character`, чтобы не дублировать код в каждом наследнике. Специфические «умения» оформляем интерфейсами: `IHealable` (умеет лечиться — только Player), `IDialogable` (умеет вести диалог с игроком — Player и NPC). Получение урона тоже можно описать интерфейсом `IDamageable` и реализовать один раз в `Character` — тогда все наследники получат его автоматически.

**Аргументы из лекции (когда что применять):**

- Абстрактный класс — когда у типов есть общее состояние и общая реализация, которую нет смысла дублировать. Это «является» (is-a): Player, Enemy, NPC — все являются персонажами.
- Интерфейс — когда нужно описать способность («умеет», can-do), особенно если она встречается у неродственных классов. Интерфейсов класс может реализовать сколько угодно, а наследоваться — только от одного класса, поэтому способности удобно комбинировать именно интерфейсами.
- Такой подход соблюдает принцип разделения интерфейсов: Enemy не тащит в себе `IHealable` и `IDialogable`, которые ему не нужны, а новые способности добавляются без переписывания существующих классов.
